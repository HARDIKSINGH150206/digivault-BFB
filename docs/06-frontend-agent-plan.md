# DigiVault — Frontend Build Plan (for the frontend coding agent)

This is the brief for an agent working on the UI only. Read `CLAUDE.md`, `docs/01-problem-and-novelty.md` and `docs/02-architecture-and-dataflow.md` first. Then read `docs/04-api-spec.md`, which is the contract you build to.

## 0. HARD RULES — read before doing anything

1. **You work only on UI files.** You may create, edit and delete files under:
   - `apps/web/src/app/**`, **except `apps/web/src/app/api/**`**
   - `apps/web/src/lib/client/**`
   - `apps/web/public/**`, but never `public/pdf.worker.min.mjs`, which is generated by `scripts/copy-pdf-worker.mjs`
   - `apps/web/INTEGRATION_NOTES.md`, which is your channel to the backend (see §9)
2. **Never touch backend or shared code.** That means `apps/web/src/app/api/**`, the server-side files directly under `apps/web/src/lib/*.ts`, `prisma/`, `packages/` (crypto-core and contracts), `apps/ai-service/`, `docker-compose.yml`, root config files and every `.env*` file. You may import from them but never edit them.
3. **Never edit `docs/`.** Build exactly to `docs/04-api-spec.md`. If the contract is wrong or missing something, write it in `INTEGRATION_NOTES.md` and keep building to the current contract. Never invent an endpoint or a field.
4. **Rules from `CLAUDE.md` that apply to the frontend:**
   - **PNG only.** Every canvas export is `image/png`. Never use JPEG or WebP, not even for thumbnails or previews of evidence.
   - **AI output never touches a hash.** Redaction suggestions only pre-select tiles. No client code may feed an AI value into `@digivault/crypto-core`.
   - **The client hashes first.** Upload always runs the crypto-core pipeline in the browser and sends `client_hash`, `merkle_root` and `tiles`. Never skip it, even to save time.
   - **`/verify` is public and stateless.** No `RequireAuth`, no `apiFetch`, no session read, and no call to any `/api/*` route. It talks only to the public Polygon RPC and the files the user drops in.
   - **The grid is 20×20.** Read `grid_size` from the API or the proof. Never hard-code a different value.
5. **Git is local only.** Stage only the paths you own (`git add apps/web/src/app apps/web/src/lib/client …`, never `git add .`). Never push, open a PR or run `gh`. The human developer does all GitHub actions.
6. **The server is the only real security check.** `can()` in `lib/client/permissions.ts` only decides which controls to show. Never treat hiding a button as access control. When a route's roles change, update the matching entry and keep the source-file comment.
7. **Honesty in the UI:**
   - Nothing says "Verified", "Anchored" or "Tamper-proof" unless that check actually passed in this session or the API says so (`anchor.status === "ANCHORED"` with a `polygon_tx_hash`).
   - Every AI suggestion shows its confidence (a whole percent) and its source (`Text layer`, `Bhashini OCR`, `IndicNER`, `Officer manual`).
   - Anything simulated, such as a seeded demo case or an Aadhaar-style login if one is ever mocked, shows a visible **"Simulated"** badge.
   - The certificate is labelled **"Unsigned — requires signature under BSA §63"**. Software never self-certifies.

## 1. What we are building (plain English)

DigiVault keeps case documents (FIRs, charge sheets, witness statements, forensic reports) tamper-evident and protects victim identity.

- An **officer uploads** a scan or PDF. The browser renders every page to a lossless PNG, cuts each page into a 20×20 grid, hashes every tile and builds a **Merkle root**. The server recomputes all of it and rejects any mismatch.
- The root is **anchored twice**: in MinIO with Object Lock, and on the Polygon Amoy `EvidenceAnchor` contract. This runs in the background (`PENDING → ANCHORED | FAILED`).
- The **AI service** suggests which tiles contain victim names, phone numbers, Aadhaar numbers or addresses. These are only suggestions: **the officer reviews and confirms them** after a fingerprint or Face ID check (with a PIN fallback). The server masks the tiles and creates a new, hash-chained, anchored **redacted version**.
- Officers can **share** the latest redacted version through an expiring, view-limited link. The original is never shared.
- **Anyone, with no login**, can drop a redacted page PNG and its `verification-proof.json` into the **Court Verification Portal** and see it checked against the blockchain.

The judges must *see* the trust story: hash, then anchor, then redact, then verify. Your most important screens are the **Version view** (redaction review), the **Upload view** (live hashing progress) and the **Verify portal**.

## 2. Stack (already in place — do not change)

- Next.js 14 App Router, React 18, TypeScript, inside the pnpm workspace (`@digivault/web`)
- Styling: plain CSS strings using the design tokens in `lib/client/theme.ts` (loaded once in `app/layout.tsx`), the `ws-*` classes in `WORKSPACE_CSS` (`dashboard/_workspace/shell.tsx`), and fonts from `lib/client/fonts.ts` (Inter for everything, JetBrains Mono for hashes). **Do not add Tailwind, a component library or a CSS-in-JS package.**
- Data: `apiJson` / `apiFetch` from `lib/client/api-client.ts`. Use plain `fetch` only on `/verify`, where it goes to the RPC and never to `/api`.
- Auth: `AuthProvider`, `RequireAuth`, `auth-storage` (1-hour session) and `useStepUp()` for the three step-up actions
- Crypto: `@digivault/crypto-core` (PDF.js → PNG → tiles → Merkle) and `pdfjs-dist`, with its worker set up in `pdf-worker-setup.ts`
- Chain reads on `/verify`: `ethers` v6, read-only
- Motion and 3D are already used on the login page (`motion`, `three-globe`). Keep them there; don't spread heavy 3D to the workspace.
- **Do not add a dependency without writing it in `INTEGRATION_NOTES.md` first.** The developer approves new dependencies.
- Port **3000**. Run with `pnpm --filter @digivault/web dev`. Typecheck with `pnpm --filter @digivault/web typecheck`.

## 4. The API layer

- The UI calls `/api/*` only through `apiJson` / `apiFetch`. Typed loaders live in `_workspace/data.ts`, or in a sibling `data-*.ts` when that file grows too big.
- Errors arrive as `ApiError(status, body)`. Map them to plain-language messages:

| Status / code | What the UI does |
|---|---|
| `401 UNAUTHENTICATED` | `apiFetch` already redirects to `/login` |
| `401 STEP_UP_REQUIRED` | re-open the step-up dialog once, then show "Verification expired — try again" |
| `403 FORBIDDEN` | "Your role can't do this", and hide that control from now on |
| `403 NO_REDACTED_VERSION` | the share panel explains "Confirm redactions first. Only redacted versions can be shared." |
| `409 HASH_MISMATCH` | show `mismatched_tile_indices` on the page grid. **Never retry automatically.** |
| `409 NOT_ANCHORED` | disable proof download until the version is anchored |
| `410` (share) | "This link has expired, been revoked or reached its view limit." |
| `429 RATE_LIMITED` | show the `Retry-After` countdown |
| `502` anchor | show the `reason` text and a **Retry anchoring** button (if `can(role, "anchorVersion")`) |

- **Polling:** use one small `usePoll(fn, ms)` hook in `lib/client/`.
  - Anchor status: poll every 3 s while `PENDING`, then stop. `anchorState()` already handles the 2-minute stall.
  - Redaction suggestions: poll every 3 s while `status === "PENDING"`, and stop on `READY` or `FAILED`.
  - Stop all polling when the tab is hidden.
- **No mock mode.** The backend, seed data and AI service already run locally (see `README.md`), and a fake hash or fake anchor would break rule 7. If the AI service is down, the suggestions endpoint returns `FAILED`. Treat that as a normal state: "Automatic suggestions unavailable — select tiles manually".

## 6. Screens

### 6.1 Login `/login`
- Service number and PIN. Show a `429` countdown. Use the same message for a wrong service number and a wrong PIN.
- A "Verify a document (no login)" link to `/verify`. It must be visible without signing in.

### 6.2 Dashboard `/dashboard`
- Stat cards: cases, documents, versions awaiting redaction review (`pendingSuggestions > 0`), and anchored versus pending or failed.
- An evidence list with an anchor badge and a "N suggestions to review" chip, plus recent activity (`buildActivity`). There is no audit-log endpoint yet (see §9).
- A **New case** form, shown only if `can(role, "createCase")`.

### 6.3 Case view `/dashboard/cases/[caseId]`
- Case header (number, type, status, department) and documents with their latest version, redacted or original tag, and anchor badge.
- An **Upload evidence** button, shown only if `can(role, "uploadEvidence")`.

### 6.4 Upload `/dashboard/cases/[caseId]/upload` (show the crypto happening)
1. Drop a PDF and enter title, document type and source type (`SCANNED` / `NATIVE`). The same form also handles a new version of an existing document via `document_id`.
2. Run the crypto-core pipeline in the browser with **visible stages**: Rendering page 3 / 5, Exporting lossless PNG, Hashing 2,000 tiles, Building Merkle tree, then the root (truncated, with a copy button).
3. Upload as multipart (`metadata` plus `page_0…page_{N-1}`).
4. On `201`: "Server independently recomputed the root ✓ — matches". Then go to the version view, where anchoring shows as pending.
5. On `409 HASH_MISMATCH`: show a red state naming the mismatched tiles. Nothing was stored, so say so.
6. Guard large files: show the page count before hashing, and keep the page responsive by yielding between pages.

### 6.5 Version view `/dashboard/documents/[d]/versions/[v]` (the core screen)
- **Header:** title, version number, a **Redacted** or **Original** tag, anchor badge, and a Polygonscan link when anchored.
- **Version chain strip:** previous hash, chain hash and Merkle root, each truncated with a copy button.
- **Page viewer:** each page PNG (from `GET pages/{i}`) with the `tile-grid` overlay.
  - AI-suggested tiles are pre-highlighted in amber, with entity type, confidence and source shown on hover or focus.
  - Officer-selected tiles show solid black with the text "Will be masked".
  - Group by entity ("Victim name — 4 tiles — 93%"), with select and clear for each group.
  - The officer can add tiles that the AI did not flag (`officer_manual`).
  - Suggestions are **not** auto-confirmed. The officer must make a selection and then confirm.
- **Suggestion states:**
  - `PENDING`: "AI is reading the document…" while polling.
  - `READY` with no suggestions: "No identifiers detected — review manually before sharing (fail-closed)".
  - `FAILED`: the message from §4.
- **Confirm redactions:** a summary ("12 tiles on 2 pages"), then the step-up dialog, then `POST …/redactions/confirm`, then navigation to the new version. That version shows "Server re-rendered and re-hashed: new root …" and anchor pending.
- **Downloads:**
  - Proof JSON, disabled until anchored with the reason shown.
  - Page PNGs.
  - Certificate PDF, which needs step-up and carries the "Unsigned" label.
  - A "Verify this in the public portal" link that opens `/verify` in a new tab.
- **Share panel:** described in 6.6.

### 6.6 Share panel (inside the version view, for `manageShares` roles)
- Fields: recipient label, expiry and maximum views. A created link is shown once, with a copy button.
- The list shows active shares with views used out of the maximum, the expiry and a revoke button. It names `sharedVersion` explicitly ("Recipients receive Version 2 (redacted)").
- With no redacted version, the panel is disabled and explains why. It never offers to share the original.

### 6.7 Share recipient `/shares/[token]` (public, the token is the credential)
- No session and no workspace chrome. Show the document title, "Redacted version N", the pages and a **Download PDF** button.
- `410` produces one clear message with no stack trace and no hint about what the token was.

### 6.8 Court Verification Portal `/verify` (public, stateless — never cut)
- Drop the redacted page PNG(s) and `verification-proof.json`.
- A **checklist** where each row shows *passed*, *failed* or *not run* in words, not only colour:
  1. Proof file is well-formed (`digivault_proof_version`, `grid_size`, `page_count`)
  2. Pages decoded and re-tiled at `grid_size`
  3. Every tile hash matches the proof. If any fail, list them and highlight the tile on the page.
  4. Recomputed root equals `proof.merkle_root`
  5. RPC reports chain `80002`
  6. On-chain root from the **hard-coded** official contract equals the root. Never use `proof.anchor.contract_address` for this lookup.
  7. `anchoredBy` is the official deployer
- **Three result states:**
  - **Verified (green):** "Verified against official DigiVault contract", showing the anchored time and the tx link.
  - **Mismatch (red):** names which check failed.
  - **Invalid — untrusted (distinct red or black):** another chain or contract, or the wrong deployer.
- Show a line explaining that the check ran entirely in this browser: "No DigiVault server was contacted."
- Must work on a phone and in a fresh incognito window.

## 7. Design direction

- **Dark theme, modelled on the Aceternity "inference" landing page:** near-black surfaces (`--ink #0a0a0a`, cards `--ink-2 #171717`), warm off-white text (`--paper #f2efe9` with 72/55/38% opacity steps), hairline borders (`--line`, white at 6%), one blue accent (`--brand #0099ff`), and emerald, amber and red only for status. Primary buttons are light pills, secondary buttons are dark pills. Headings are Inter 500 with tight tracking. Always use the `var(--…)` tokens from `lib/client/theme.ts`, never new hex values. Page images of evidence stay on white.
- **Show trust visually, honestly:** hashes in a monospace font, truncated as `3f9a…e21c` with a copy button. Show anchor states with a text label, the tile grid with clear masked and unmasked states, and confidence as a bar plus a whole percent.
- **Never colour alone:** every chip, badge and checklist row has text.
- **Accessibility:** tile grid cells are focusable buttons with `aria-pressed` and a label ("Page 1, row 3, column 8, suggested: victim name 93%"). Dialogs trap focus. Every interactive element gets visible `:focus-visible` styling.
- **Times:** IST, as `11 Oct 2026, 9:40 pm`. Use relative times only in activity lists.
- **Every data view has loading, empty and error states.** Never show raw JSON or stack traces.
- **Layouts:** the workspace is desktop-first but usable at 1024 px. `/verify`, `/shares/[token]` and `/login` work on phones with a 16 px gutter and no horizontal scroll.

## 10. Demo click path (superseded by `docs/05-demo-golden-path.md`)

1. Log in as an Investigating Officer (`DL/2019/3301`) and open the seeded case.
2. Upload a messy multi-page FIR from `public/sample-firs/`. Watch the hashing stages, then see "Server recomputed ✓" and the anchor pending.
3. The anchor turns **Anchored**. Open the Polygonscan link.
4. Review the AI suggestions (victim name, phone, Aadhaar), add one tile manually, confirm with the fingerprint or PIN check, and see v2 created and anchored.
5. Download the proof and the page PNG, then create a share link and open it in incognito to see only the redacted version.
6. Open `/verify` in incognito, drop the files and see **Verified**.
7. Edit one pixel of the PNG, drop it again and see **Mismatch at tile N**, with the tile highlighted.
8. Log in as a Court Official to show read-only access with proof and certificate download.
